# 라이브 스트리밍 서비스 시스템 설계 문제

##  문제 개요
당신은 **Twitch / YouTube Live 와 유사한 라이브 스트리밍 플랫폼**을 설계하려 한다.

---

##  요구사항

1. 누구나 **라이브 방송**을 시작할 수 있어야 한다.
2. 시청자는 **수만 ~ 수십만 명 규모**까지 동시에 참여할 수 있다.
3. **1~5초 이하의 낮은 지연(Low Latency)** 재생을 지원해야 한다.
4. 방송은 **종료 후 VOD 형태로 저장**될 수 있어야 한다.
5. **채팅 시스템은 본 문제의 설계 범위에서 제외한다.**

---

##  문제 풀이 시 반드시 포함해야 하는 내용
1. CDN 활용 전략
2. 스트리밍 전송 방식 선택

## 1. 스트리밍 전송 방식
| 기준 | RTMP | SRT | WebRTC |
|------|------|-----|---------|
| **누구나 방송 시작 가능** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ |
| **해외/모바일 안정성** | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| **Low Latency 재생과의 궁합** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **구현 난이도** | 쉽다 | 중간 | 어렵다 |
| **대규모 스트리밍 파이프라인 적합성** | 최적합 | 최적합 | 부적합(고비용) |

- RTMP 선택 이유
  - SRT가 더 안정적이지만 설정·운영 복잡성이 높음 
  - 요구사항 중 **누구나 라이브 방송을 시작할 수 있어야한다**에  가장 만족한다고 판단

## 2. 라이브 스트리밍 서비스 아키텍처 흐름
1. 사용자 (스트리머)
   - 방송을 시작하면 OBS(또는 앱)는 RTMP 프로토콜을 사용해 비디오·오디오 데이터를 Ingest 서버로 실시간 전송
2. Ingest 서버
   - 스트리머가 보낸 RTMP 스트림을 받아 원본 비디오를 트랜스코더로 전달
3. 트랜스코더
   - 원본 비디오를 여러 화질과 비트레이트의 비디오 스트림으로 변환
4. 패키저
   - 트랜스코딩된 여러 화질의 비디오 스트림을 받아 시청자가 재생할 수 있는 스트리밍 포맷으로 변환
   - 스트리밍 포맷은 **LL-HLS** 규격에 맞게 각 화질 별로 **세그먼트 파일 + 파트 파일 + M3U8(플레이리스트)** 형태로 생성
     - 재생 지연을 2~5초 수준으로 낮출 수 있기 때문에 LL-HLS 규격을 사용
5. Origin 서버
   - 패키저가 생성한 파일들은 모두 Origin 서버에 저장, 이 Origin에 저장된 파일을 전 세계 CDN 노드가 가져감
   - CDN은 글로벌 캐시 서버 네트워크로 구성되어 있어, 시청자와 가장 가까운 노드에서 데이터를 전달해 지연을 최소화함
6. 시청자
    - CDN에서 파일들을 요청해 전달받음
    - 플레이어는 마스터 플레이리스트를 기반으로 네트워크 상황에 따라 적절한 화질을 자동으로 결정
    - Part 단위의 조각 파일을 실시간으로 다운로드하며 즉시 재생 시작
    - 뒤이어 세그먼트 파일을 받아 버퍼링을 안정화하며 지속적으로 재생을 이어감

## 3. VOD 저장
1. Ingest 서버가 방송이 종료됨을 감지하고, 패키저에 방송 종료 이벤트 전달
2. 패키저는 마지막 세그먼트/파트를 플레이리스트에 반영하여 최종 재생 목록을 완성
3. 마지막에 태그를 추가해 더 이상 새 조각이 없음을 표시
4. 이렇게 완성된 플레이리스트 + 세그먼트 파일들을 그대로 VOD용 HLS로 노출하여 시청자가 다시보기(VOD) 형태로 재생할 수 있게 만듦
